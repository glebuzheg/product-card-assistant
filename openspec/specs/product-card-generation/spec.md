# product-card-generation Specification

## Purpose
Подготовка проверяемых русскоязычных черновиков карточек B2B-приборов на основе предоставленных данных с явным указанием пропусков и ошибок генерации.

## Requirements

### Requirement: Validated JSON input
Сервис SHALL принимать POST /generate с обязательным непустым name и необязательными manufacturer, specs и description; строки и словарь SHALL иметь ограничения размера, неизвестные поля и неверные типы SHALL отклоняться.

#### Scenario: Invalid input
- **WHEN** JSON некорректен, имя пустое или тип поля неверен
- **THEN** ответ имеет HTTP 422 без раскрытия исходных секретов

#### Scenario: Oversized body
- **WHEN** тело запроса превышает 64 KiB, в том числе при потоковой передаче
- **THEN** сервис отвечает HTTP 413 до вызова LLM

### Requirement: Product card output
Успешная карточка SHALL иметь status=ok, заголовок 1–70 символов, описание 800–1200 символов, характеристики из specs, 3–5 непустых различных поисковых запросов, commercial-блок и missing_fields. Длины SHALL включать пробелы.

#### Scenario: Complete product
- **WHEN** переданы сведения о приборе и модель возвращает прошедший проверки ответ
- **THEN** сервис возвращает JSON со всеми полями и исходными значениями характеристик

### Requirement: Missing information
Сервис SHALL явно отмечать отсутствие производителя, описания и пустые значения переданных характеристик. Если нет ни описания, ни непустых specs, SHALL возвращаться needs_clarification без вызова API, с null вместо текстов и пустыми поисковыми запросами.

#### Scenario: Name alone
- **WHEN** передано только название
- **THEN** сервис возвращает needs_clarification и запрос описания или характеристик

#### Scenario: Partial specifications
- **WHEN** известна хотя бы одна характеристика, а другая передана пустой
- **THEN** генерация допустима, но неизвестная характеристика имеет значение «данных нет» и включена в missing_fields

### Requirement: Grounded generation
Модель MUST получать запрет на новые технические факты и исполнение инструкций внутри описания. Сервис SHALL проверять цитаты утверждений, ссылки и цитаты входных полей, а также отсутствие новых технических чисел; характеристики SHALL копироваться кодом из входа.

#### Scenario: Unsupported value
- **WHEN** ответ содержит техническое число, отсутствующее во входе, или неверную ссылку на источник
- **THEN** карточка не выдаётся; допускается одна исправляющая попытка, затем HTTP 502

#### Scenario: Model number is not a specification
- **WHEN** число имеется только в названии прибора, но модель использует его как техническую характеристику
- **THEN** такое числовое утверждение не принимается как подтверждённое

### Requirement: Safe provider errors
Сервис SHALL ограничивать время вызова API и не раскрывать ключи, traceback или сырые ответы провайдера. Нет настройки — HTTP 503, rate limit — 429, таймаут — 504, ошибка API, отказ или незавершённый ответ — 502.

#### Scenario: Provider timeout
- **WHEN** API не отвечает в отведённое время
- **THEN** клиент получает HTTP 504 с безопасным сообщением

#### Scenario: Model refuses
- **WHEN** модель отказывается или ответ прерван
- **THEN** клиент получает HTTP 502 вместо непроверенной карточки

### Requirement: Reproducible submission
Репозиторий SHALL содержать lock-файл, инструкции запуска, входы двух товаров с источниками, описание промпта, ограничений и тесты без платных вызовов. Реальные выходы SHALL сохраняться только после настоящего вызова API и ручной сверки.

#### Scenario: No API credentials
- **WHEN** ключ ещё не предоставлен
- **THEN** тесты выполняются без него, а реальные выходы не подменяются искусственными примерами
