# Product Card Assistant — проектное решение

Дата: 6 ноября 2026. Статус: предложение для согласования, реализации пока нет.

## Задача и границы

Локальный Python-сервис готовит русскоязычный черновик карточки контрольно-измерительного прибора для B2B-магазина. Основание — предоставленное тестовое задание: https://drive.google.com/file/d/1CcfOkv2K2CG8k7Ys1X430QRH_ZR-IGT6/view.

Успешный результат содержит SEO-заголовок до 70 символов, SEO-описание 800–1200 символов включительно, характеристики, 3–5 поисковых запросов и краткий блок о покупателях и решаемых задачах. Длины считаются в Python через len(), включая пробелы. Недостающие сведения перечисляются явно; неизвестные значения обозначаются «данных нет».

Не входят: CMS, база данных, авторизация, массовый импорт каталога, деплой, отдельный frontend и автоматическая публикация карточек. Сервис запускается локально и возвращает черновики для проверки человеком.

## Выбранный подход

Пользователь выбрал Python, FastAPI и OpenAI API; работа ведётся по SDD с OpenSpec. FastAPI предпочтён Streamlit, поскольку задача сформулирована как сервис с JSON-входом; встроенная страница /docs достаточна для демонстрации. Скрипт командной строки был бы короче, но хуже показывает работу сервиса.

Предлагаемые инструменты: Pydantic для схем и проверок, официальный OpenAI SDK с Responses API и Structured Outputs для генерации, uv и lock-файл для зависимостей, pytest для тестов, Ruff для проверки кода. Конкретная модель задаётся через OPENAI_MODEL; доступность и качество выбранной модели проверяются реальными вызовами, а не предполагаются по названию. Python 3.12 — предлагаемый минимальный runtime.

## Вход и выход

POST /generate принимает объект с name, manufacturer, specs (словарь строковых характеристик), description. Название обязательно и не может состоять из пробелов; остальные поля могут отсутствовать или быть пустыми. Неверные типы и неизвестные поля отклоняются, входные строки и количество характеристик имеют разумные ограничения размера. URL из данных не открываются сервисом.

Ответ содержит status, seo_title, seo_description, characteristics, search_queries, commercial_block и missing_fields. Для результата status=ok обязательны все ограничения задания. Код возвращает status=needs_clarification без вызова API, если одновременно нет непустого description и ни одной непустой характеристики specs; название и производитель сами по себе недостаточны. При этом текстовые поля результата равны null, поисковые запросы пусты, а missing_fields содержит запрос описания или технических характеристик. Если описание или характеристики есть, выполняется генерация; неудача проверок после повторной попытки означает HTTP 502, а не needs_clarification. Неполный ввод сам по себе не запрещает генерацию: успешная карточка может содержать список пробелов в данных.

Характеристики формируются программно из specs; модель не может дописать или изменить их значения. Отсутствующие manufacturer и description отражаются в missing_fields; пустые значения явно переданных характеристик показываются как «данных нет». Не вводим универсальный список обязательных характеристик для всех приборов: диапазоны, питание и точность важны не для каждого типа товара.

## Генерация и проверка

Поток: проверка входа → подготовка известных фактов и пропусков → один вызов OpenAI → проверка ответа → JSON для копирования. Системный промпт запрещает новые технические факты, домыслы о сертификации, наличии, цене, гарантии и совместимости. Входное описание рассматривается как данные, а не как инструкции модели.

Внутренняя схема ответа модели содержит готовые тексты и отдельный список технических утверждений с указанием блока ответа, точной цитаты утверждения из этого блока, пути входного поля и точной цитаты источника. Проверяем наличие утверждения в указанном блоке, существование входного поля, соответствие цитаты источнику и отсутствие новых числовых технических значений во всех текстовых полях; значения из названия модели не считаем доказательством диапазона или точности. Тексты возвращаются целиком, итоговую таблицу характеристик собирает код. Проверка не доказывает, что цитата логически подтверждает утверждение, и не гарантирует, что модель перечислила все утверждения: два примера дополнительно проверяются вручную по источникам. Отдельную модель-судью и автоматический семантический разбор в MVP не добавляем.

После ошибки формата, длины или проверки фактов допускается одна повторная генерация с указанием ошибок. Если исправить результат не удалось, сервис возвращает понятную ошибку, а не непроверенную карточку. При отказе модели и незавершённом ответе успешная карточка также не выдаётся. Политика повторов SDK задаётся явно, чтобы не умножать платные вызовы скрытыми повторами; для прототипа автоматические транспортные повторы отключены.

## Ошибки и секреты

Некорректный JSON и неверные поля — HTTP 422 с понятным описанием; превышение лимита тела — 413. Отсутствие настройки API — 503, превышение лимитов провайдера — 429, таймаут — 504, прочие ошибки провайдера или непроверенный ответ — 502. Сообщения не раскрывают ключи, внутренние ответы провайдера или traceback.

OPENAI_API_KEY и OPENAI_MODEL задаются через окружение; локальный .env, если используется, исключён из Git. В репозиторий попадает только .env.example без секретов. Не записываем ключи и полные тела запросов в логи. На реальных демонстрациях в OpenAI отправляются только публичные данные двух выбранных товаров.

## Примеры и источники

В XML-каталоге https://www.souz-pribor.ru/yml/any/feed.xml обнаружено 47 974 предложения. Есть названия, типы, производители и артикулы, но нет технических описаний и диапазонов измерений.

Два выбранных товара: дифференциальный манометр testo 510 (offer 58444, артикул 0563 0510) и пищевой термометр testo 105 (offer 64163, артикул 0563 1051). Технические сведения берутся с соответствующих страниц https://www.souz-pribor.ru/product/testo-510/ и https://www.souz-pribor.ru/product/testo-105/. Перед сохранением JSON проверяются конкретная модификация, единицы и точное соответствие источнику; происхождение и дата получения описываются отдельно.

В репозиторий сохраняются два небольших входных JSON и два настоящих результата API, а не весь XML на 35 МБ. Ещё один небольшой неполный пример показывает обработку пропусков. Подготовка примеров выполняется до вызова сервиса: автоматический парсер сайта в продукт не входит.

## Структура и OpenSpec

Предлагаемое имя: product-card-assistant. Локальная папка: ~/projects/product-card-assistant; GitHub-владелец подтверждён подключением: glebuzheg. По умолчанию предлагается приватный репозиторий, публичность можно изменить по просьбе пользователя.

Минимальная структура реализации: пакет приложения с API, схемами и генерацией; tests/; examples/; README.md; pyproject.toml; uv.lock; .env.example; .gitignore. Никаких слоёв репозиториев, агентов и универсального адаптера для разных LLM.

После согласования документ переносится в репозиторий, затем инициализируется OpenSpec. Одно изменение generate-product-card содержит proposal.md, design.md, tasks.md и спецификации со сценариями приёма JSON, генерации, проверки фактов, нехватки данных и ошибок. Затем — тесты, реализация, проверка сценариев и архивирование изменения только после выполнения задач. Структура и команды уточняются по установленному OpenSpec 1.15.0.

## Критерии готовности

- Два реальных примера проходят ограничения длины и количества запросов; все технические утверждения сверены с сохранёнными входными данными.
- Тесты покрывают неверный JSON, пустое название, неправильные типы, пропуски, изменённые характеристики, новые технические числа, ошибки длины, одну корректирующую попытку, отказ модели, таймаут и ошибки API.
- Проверки не используют платный API; отдельно выполнен и отмечен реальный прогон двух товаров, если предоставлен доступ к OpenAI API.
- README содержит проверенные инструкции запуска и примеры, описание промпта, решения, ограничения и возможные улучшения; секретов и полного каталога в Git нет.
- OpenSpec проверен, тесты и Ruff пройдены, содержимое GitHub-репозитория проверено после публикации.

## Ограничения и решения автора

Прототип не даёт абсолютной гарантии отсутствия смысловых ошибок LLM; карточка остаётся черновиком. Проверка чисел и цитат не заменяет проверку предметным специалистом. Нет доступа к ключу или модели — значит реальные примеры остаются невыполненным пунктом и не подменяются вымышленными результатами.

Решения автора для согласования: Python 3.12; JSON через /docs без отдельной формы; один endpoint; одна корректирующая попытка; приватный GitHub-репозиторий; два товара Testo; отсутствие БД и деплоя.
