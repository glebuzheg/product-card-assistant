# Product Card Assistant

Локальный сервис на Python для подготовки русскоязычных черновиков карточек контрольно-измерительных приборов. Принимает JSON, вызывает OpenAI и возвращает JSON для копирования. Это прототип по тестовому заданию, без базы данных и деплоя.

## Быстрый запуск

Нужны Python 3.12+, [uv](https://docs.astral.sh/uv/getting-started/installation/) и доступ к OpenAI API.

```bash
git clone https://github.com/glebuzheg/product-card-assistant.git
cd product-card-assistant
uv sync --locked
cp .env.example .env
```

В `.env` укажите `OPENAI_API_KEY` и `OPENAI_MODEL`. Не отправляйте ключ в чат и не добавляйте файл в Git. В примере указана `gpt-4.1-mini`, поддерживающая Structured Outputs; доступность модели зависит от аккаунта. Это пример настройки, а не утверждение о выполненном реальном прогоне.

```bash
uv run uvicorn product_cards.api:app --host 127.0.0.1 --port 8765
```

Откройте http://127.0.0.1:8765/docs, выберите `POST /generate` → Try it out и вставьте содержимое одного из файлов `examples/*.input.json`. Отдельного веб-интерфейса нет.

Из другого терминала:

```bash
curl --fail-with-body http://127.0.0.1:8765/generate \
  -H 'Content-Type: application/json' \
  --data-binary @examples/testo-510.input.json

curl --fail-with-body http://127.0.0.1:8765/generate \
  -H 'Content-Type: application/json' \
  --data-binary @examples/testo-105.input.json
```

Первый вызов и, при необходимости, одна корректировка платные. Встроенные транспортные повторы SDK отключены; каждый вызов ограничен 45 секундами. Перезапустите процесс после изменения `.env`.

## Вход и результат

```json
{
  "name": "Название прибора",
  "manufacturer": "Производитель",
  "specs": {"Питание": "", "Корпус": "ABS"},
  "description": "Фрагмент технического описания"
}
```

`name` обязателен (1–200 символов). Остальные поля необязательны: `manufacturer` — до 200 символов, `description` — до 20 000, `specs` — до 100 строковых характеристик; ключ до 200, значение до 1000 символов. Пробелы по краям удаляются. Неверные типы, неизвестные поля и пустые имена характеристик отклоняются. Общий размер запроса — не более 64 KiB.

Успешный ответ:

- `status: "ok"`;
- `seo_title`: до 70 символов;
- `seo_description`: 800–1200 символов с пробелами;
- `characteristics`: исходные значения из `specs`, пустые заменены на «данных нет»;
- `search_queries`: 3–5 различных поисковых запросов;
- `commercial_block`: кому подходит прибор и какие задачи решает;
- `missing_fields`: отсутствующие сведения, например `manufacturer`, `description`, `specs` или `specs.Питание`.

Производитель и описание могут отсутствовать: если имеются технические факты, генерация допустима и пробелы отмечаются в `missing_fields`. Универсальный набор обязательных характеристик не навязывается всем типам приборов.

Если нет ни описания, ни непустых характеристик, API не вызывается: `status` будет `needs_clarification`, текстовые поля — `null`, запросы — пустым списком. Этот сценарий работает без ключа:

```bash
curl --fail-with-body http://127.0.0.1:8765/generate \
  -H 'Content-Type: application/json' \
  --data-binary @examples/incomplete.input.json
```

## Как устроен промпт и проверка фактов

Полный промпт находится в `product_cards/generation.py`. Он задаёт роль редактора, русский язык, длины, формат и запрет на добавление свойств из памяти. Входной JSON передаётся как данные; инструкции внутри описания запрещено выполнять. Модель не получает доступ к поиску, сайтам и инструментам.

OpenAI Responses API вызывается со Structured Outputs и JSON Schema из Pydantic. Внутренний ответ содержит тексты и `evidence`: цитату утверждения, блок ответа, путь входного поля и точную цитату источника. Код проверяет наличие этих цитат и отсутствие новых числовых значений; число из названия модели разрешено только внутри самого названия. Таблицу характеристик собирает код, а не LLM. Служебный evidence не включается в публичный ответ.

После ошибки формата, длины или проверки фактов допускается одна корректирующая попытка. Если она не помогла, возвращается ошибка, а не непроверенная карточка. `store=False` отключает сохранение объекта Responses для последующего получения; это не обещание отсутствия любых журналов у провайдера. В OpenAI передаются входные данные товара: не отправляйте закрытые сведения без разрешения.

## Ошибки

| HTTP | Значение |
|---|---|
| 422 | Неверный JSON, типы или поля |
| 413 | Тело больше 64 KiB |
| 503 | Не заданы ключ или модель |
| 429 | Лимит провайдера исчерпан |
| 504 | Таймаут OpenAI |
| 502 | Ошибка API, отказ/обрыв ответа или неуспешная проверка черновика |

Ошибки не возвращают входные значения, ключи, сырой ответ провайдера или traceback. Сервис не ведёт журнал тел запросов.

## Примеры и их статус

Подготовлены `examples/testo-510.input.json` и `examples/testo-105.input.json`. Происхождение, артикулы и исключённые спорные сведения описаны в [examples/SOURCES.md](examples/SOURCES.md). Большой XML-каталог не включён в репозиторий.

Реальные выходы должны находиться в `examples/testo-510.output.json` и `examples/testo-105.output.json`. Если этих файлов нет, реальные результаты ещё не получены: нужен рабочий доступ и доступная API-квота. Последний реальный прогон и его статус описаны в [examples/RUN.md](examples/RUN.md). Искусственные ответы из тестов не выдаются за результат модели. После генерации требуется вручную сверить оба текста, единицы, условия и модификацию прибора с входом.

## Разработка и OpenSpec

```bash
uv run pytest -q
uv run ruff check .
uv run ruff format --check .
```

Тесты работают без ключа и сети: на границе HTTP используется `httpx.MockTransport`, остальной путь, включая официальный SDK, схемы и маршрут, настоящий. Локальный `.env` отключён в тестах. В текущей версии Starlette может появляться предупреждение о будущем переходе TestClient с httpx на httpx2; проверки при этом проходят.

GitHub Actions запускает те же проверки для push и pull request. Его успешное выполнение проверяется отдельно от локального запуска.

Проект ведётся по SDD: предложение, требования со сценариями, технический дизайн и задачи находятся в `openspec/changes/generate-product-card/`. Согласованный дизайн — `docs/design.md`, план — `docs/implementation-plan.md`. Для проверки артефактов нужен отдельно установленный OpenSpec (проект инициализирован версией 1.15.0):

```bash
openspec validate --all --strict
openspec status --change generate-product-card
```

Изменение остаётся открытым, пока не выполнены все задачи, включая два настоящих примера API. После завершения оно переносится в архив, а требования — в `openspec/specs/`.

## Ограничения и возможные улучшения

Числовой фильтр и цитаты не доказывают смысловую достоверность текста: модель может неверно связать известное число с единицей, неправильно пересказать источник или пропустить утверждение в evidence. Значения, записанные словами, тоже не проверяются числовым фильтром. Проверка может отклонить корректное переформатирование числа или единиц. Поэтому результат — черновик для проверки человеком, а не готовая публикация.

Сервис не определяет все обязательные характеристики каждого типа прибора и не разрешает противоречия в паспортах. Слишком бедные сведения могут не дать качественный текст нужной длины и привести к безопасному отказу после корректировки.

Следующие улучшения при реальной необходимости: набор эталонных оценок на разных приборах, проверка единиц и диапазонов по полям, указание конфликтующих источников, простой интерфейс редактора. Для общедоступного размещения понадобятся авторизация и ограничения частоты запросов; текущий запуск рассчитан на localhost.
